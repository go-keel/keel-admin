# Frontend forms, confirmations and list page state

Read this before writing a form, a confirmation, a dialog or drawer, a success message or a list page's URL state.
The first half is the rules (which content goes in which container, how forms validate, whether to say something after
success); the second half is the steps to follow. This page is a frontend convention of keel-admin and has no
counterpart among the guides in `docs/guides/`. Live example: the kernel's `web/src/routes/_app/sys/-users.tsx` (one
form for create and edit, step-up, a composite control).

## Rules

### Container roles

**A form to submit goes in a dialog; confirming an action uses a dialog by default, and a button exposed on the page
may use a popover instead; a drawer is only for viewing; a related list that needs paging goes back to its own page.**
Not chosen: by noun and verb (viewing and editing in a drawer whose open state is in the URL), because a one-field
form then slides out a whole panel, an outside click silently drops a half-filled form, and the URL state reopens on
Back and loses its context on refresh; by form length (short in a dialog, long in a drawer), because every form would
weigh its field count, while long forms use the dialog's wide sizes. The cost: a refresh closes whatever popped up and
returns to page 1, and the record being edited cannot be shared as a link; a detail that must be shareable gets its own
page. Seven supporting rules:

1. **Form dialog** (`FormDialog`): create and edit share one form and one dialog, and whatever the same people can
   change under the same threshold is merged into one submit. **No edit form sits on a page, settings pages
   included**: the page shows only the current values, a button opens the dialog to change them, and the initial
   values are fetched when it opens (`docs/adr/admin-0006-form-initial-values-fetch-detail.md`); the model is the
   profile page. Three widths (`size`), chosen only from these three: the default for ordinary forms with few fields,
   `wide` for large forms that fit in two columns (role configuration), `xl` for settings forms that would run past
   one screen even in two columns and need three. Clicking outside does not close it; closing after changes first asks
   whether to discard them.
2. **Action dialog** (`ActionDialog`) is the default container for confirming one action and collecting its
   parameters on the way (disable, delete, reset, collecting the step-up code). **Greying out while submitting, refusing
   to close during the request, staying put on failure and closing itself on success all belong to the container**
   (as with `ConfirmPopover`); the page supplies only a confirm function. While parameters the action collects are not
   filled in yet, grey out the confirm button with `confirmDisabled`.
3. **Popover confirmation** (`ConfirmPopover`; on a table row, the `confirm` of a `RowAction`): a button exposed
   directly on the page (on a row, in the page header, on the bulk bar) may use a popover next to the button instead;
   the page decides by consistency across the page and by feel. An action tucked into the "⋯" menu can only use a
   dialog (`RowActions` routes it automatically). Within one page, one action does not mix the two.
4. **Popovers** (Popover / Select) also serve instant choices that change no data (time zone, language, preset), and
   reversible "tick a few, look, then decide" values (permission preview). Color mode has only two sides and is one
   toggle button in the header; the login page has no color mode toggle.
5. **Drawer** (`ResourceSheet`): viewing one row's information, plus related summaries that fit on one screen (when
   there are more, show only the first few plus "View all ↗"); each related summary is shown or hidden by its own view
   permission. Whether it holds buttons is up to the page. **The list hands the drawer only the ID, and the drawer
   fetches the details by that ID**, and the same goes for dialogs, so what is shown is never a stale copy of a list
   row. The exceptions are inline edits, and a name used only to recognise the object (in a confirmation prompt or a
   title), which may travel with the ID while the action itself sends only the ID
   (`docs/adr/admin-0006-form-initial-values-fetch-detail.md` "Viewing also goes by ID"). A dialog may float over a
   drawer; **a drawer never opens another drawer**.
6. **A related list that needs paging opens its own list page in a new browser tab, with the filter values carried
   along** (a real `<a href target=_blank rel=noopener>`, with ↗ in the text), instead of embedding a copy in the
   current page. A row-level entry goes in the `href` of a `RowAction`, **generated by the router from the target
   page** (`router.buildLocation({ to, search }).href`, never assembled by hand, so a misspelled key fails to
   compile); the shared part renders it as a real link with ↗. **Do not use `window.open`**: it takes away middle
   click, Cmd+click and right-click "copy link". This is about **jumping from a row to the list it relates to** (for
   example "View articles in this category ↗" on each row of article category management), not a header button that
   jumps somewhere the sidebar menu already goes: that is a duplicate entry and is not built.
7. **Flows with an order**: a flow that is the page itself (forced binding at login) unfolds in place; one started
   from a button on a page (binding an authenticator in the profile) goes into a plain dialog (`Dialog`) that does not
   close on an outside click.

An overlay you build yourself from `Dialog` / `Sheet` wraps its content in `KeepLastOpen`
(`web/src/components/containers.tsx`): after closing it holds the last frame until the exit animation finishes;
otherwise the state the page clears on close is drawn as an empty box during the exit. The kernel's four containers
already wrap it, so do not wrap them again.

On mobile, form dialogs and drawers go full screen and action dialogs stay centred; the rules are the same. **A form
has at most one step-up point** (`OtpField`); the reasons are in
`docs/adr/admin-0007-operation-split-and-step-up-placement.md`.

### Forms

**react-hook-form + zod, with fields written the way the shadcn docs write them (`Controller` + `Field`); the kernel
does not wrap inputs**, so a field reads exactly like the upstream docs and gains no second API to learn. The
exceptions are controls shadcn has no ready component for: the password input, the one-time code input and the date
and time pickers (see `docs/admin/pages.md` "Controls and sizes"). The kernel provides only containers and logic:
`FormDialog`, `useZodForm` in `lib/form.ts` (zod wired in, validation timing set, back to the initial values on every
open, revalidation after a language switch), the shared error copy, and rule functions such as `tr()` and
`ipWhitelist()`. Rules are written in zod and aligned with the constraints in the server's proto; the copy for common
errors comes from the kernel, and specific copy uses `tr()` (the entry is looked up at validation time, so a language
switch does not leave it in the old language). The first submit validates everything, later changes validate as you
go; **the submit button stays clickable**: fields that fail turn red with the reason and the cursor jumps to the
first one, and the button is greyed out only while submitting, or while editing before the details have arrived.
Server errors are still shown as a toast and are not attached to fields. Required controls carry `aria-required` (a
group of checkboxes carries `data-required` on its `FieldSet`), and the label gets a red asterisk automatically.

**Form initial values always come fresh from the detail endpoint (`Get<Resource>`), never from list rows or frontend
cache; correspondingly, list endpoints send only the fields the list shows.** Writing stale data back is data loss,
not a display lag: a form filled from an old list row silently overwrites whatever changed since
(`docs/adr/admin-0006-form-initial-values-fetch-detail.md`). Every editable resource has a detail endpoint; without
one, build no edit entry.

**Operations are split along permission boundaries, not by how many backend endpoints there are**: whatever the same
people can change under the same threshold (permission code, with or without step-up) is merged into one form and one
submit, and only what needs different permissions is split. **A form has at most one step-up point**, so the user
enters a one-time code once per submit (`docs/adr/admin-0007-operation-split-and-step-up-placement.md`).

**The frontend never infers whether a configuration takes effect.** Function codes, data scope and management
boundary are orthogonal dimensions and none can be inferred from another, so a frontend guess is wrong in exactly the
cases that matter. To tell people whether a setting has an effect, the server returns the verdict; otherwise say
nothing (`docs/admin/permission-model/README.md` §3).

### Success messages

**Say something after success only when the screen shows no change.** Failure is always a toast
(`docs/admin/errors.md` "The frontend has two rules"); success is not. There is one test: **after the action, does the
interface itself tell the user it worked?** A new row in the list, a status column changing from "Active" to
"Disabled", an authenticator column changing to "Not bound": the screen has already said it, and another "Operation
succeeded" says the same thing twice; after a few clicks it is noise, and the messages that matter drown in it.
Conversely, resetting a password, forcing a sign-out, changing super administrator status, or editing a role where
only its permissions changed: after the click the screen looks as if nothing happened, so a message is required. One
case is stricter: **a result that looks like a failure must be explained**. After changing the password in the
profile, the session ends at once and the user is sent back to the login page; without a sentence like "Your password
has been changed. Sign in again with the new password.", what the user sees is "the form cleared and I was thrown
out".

The container sends the message; the page supplies only the copy, through `success` on `ActionDialog` /
`ConfirmPopover` / `FormDialog` (`confirm.success` on a `RowAction`). Without it, nothing is sent. **Do not call
`toast.success` in a page**: what happens after success (closing the dialog, showing the message) belongs to the
container, for the same reason as "grey out while submitting, stay put on failure". The copy states what happened and
its consequence on the user's side (such as "All sign-in sessions have ended"), never "Operation succeeded" and never
implementation details (the criteria for user-facing text: `docs/practices/user-text.md`). The two
defaults point in opposite directions on purpose: failure speaks by default because a forgotten handler swallows an
error silently; success stays silent by default because a missing confirmation costs one more look at the screen,
while too many messages teach users to ignore all of them. What is judged is this result, not the action: the same
action may change the screen once and only be submitted for approval another time, so an action with more than one
outcome passes the container's `success` a function that picks the copy from the confirm function's return value
(`confirm.success` on a `RowAction` takes fixed text only; such an action opens an `ActionDialog` from `onSelect`). How
to write it: see "Confirming an action" below.

## A dialog form

1. **Rules**: `z.object({...})`, with constraints aligned with `buf.validate` in the server's proto; the server is
   still the last gate. Required text is `.trim().min(1)`, so the error reads "Required" rather than "At least 1
   character". When create and edit have different required fields, write one schema for each and pick by `id`.
2. **Form instance** (`web/src/lib/form.ts`): use `useDetailForm` when initial values are fetched (edit), and
   `useZodForm` for create-only forms:

   ```tsx
   const { form, detail } = useDetailForm(schema, {
     open, // back to the initial values on every open
     defaultValues: EMPTY, // create
     detail: id ? { query: xxxDetailQueryOptions(id), toValues } : undefined, // edit
   });
   // pass detail to FormDialog's queries: saving is blocked until the details arrive or when they fail
   ```

   It handles fetching the details fresh (refetched on every open, dropped on close, sent only while open) and
   filling the form only once; the query options need not say so.

3. **Shell** (`FormDialog` in `web/src/components/containers.tsx`):

   ```tsx
   <FormDialog
     open={open}
     onClose={onClose}
     title={id ? t('xxx.edit') : t('xxx.create')}
     form={form}
     needOtp // only when step-up is required: the code is passed to onSubmit with the submit
     // details and options: skeleton while pending, error and retry on failure; no saving in either case
     queries={[detail, deptsQuery]}
     onSubmit={(v, otp) => saveXxx(id, v, otp)}
   >
   ```

   Every piece of data the form uses (the details when editing, dropdown options) goes into `queries`; disabled ones
   (the details when creating, options not fetched for lack of permission) do not count. Anything else to wait for
   (such as filling finishing) goes in `loading`.

   `onSubmit` throwing = failure (the request layer has shown the toast), and the dialog stays put; returning `false`
   = the page blocked it itself (call `form.setError(...)` first to mark the field), and it also stays put; anything
   else is success and the dialog closes. Not closing on an outside click, confirming discarded changes and greying
   out while submitting are all handled by `FormDialog`; the page writes none of them. For a large form, pick
   `size="wide"` or `size="xl"` by rule 1 under "Container roles" above.

4. **Fields** follow the shadcn docs, one `Controller` per field:

   ```tsx
   <Controller
     name="name"
     control={form.control}
     render={({ field, fieldState }) => (
       <Field data-invalid={fieldState.invalid}>
         <FieldLabel htmlFor="xxx-name">{t('xxx.name')}</FieldLabel>
         <Input {...field} id="xxx-name" aria-required aria-invalid={fieldState.invalid} />
         {fieldState.invalid ? <FieldError errors={[fieldState.error]} /> : null}
       </Field>
     )}
   />
   ```

   - Required: the control carries `aria-required`, and the label gets a red asterisk automatically; when a group of
     checkboxes is required as a whole, put `data-required` on the `FieldSet`.
   - Number inputs: `value={String(field.value)}`, converting back to a number in `onChange`.
   - `Select` / `Switch` / `Checkbox`: connect `field.value` and `field.onChange` to their controlled props.

5. **Custom-drawn composite controls** (such as the permission tree): read with `form.watch(...)`, write with
   `form.setValue(name, value, { shouldDirty: true })`. Without `shouldDirty`, "discard unsaved changes" does not see
   that it changed.

## Error copy

- Required, length, numeric bounds and minimum selections are mapped to `form.*` entries by `web/src/lib/form.ts`;
  schemas carry no copy for them.
- When the message must say something specific, use `tr('entry', params)`:
  `z.string().refine(ok, { error: tr('xxx.bad') })`. **Do not write `t('xxx.bad')`**: that is a string fixed when
  the page loads, so revalidation after a language switch still shows the old language. `optionalEmail()` is a ready
  example.
- Server errors are still shown as a toast by the request layer and are not attached to fields.

## Confirming an action

- Use `ActionDialog` by default (`open` / `onOpenChange` / `onConfirm(otp)` / `needOtp` / `destructive`).
  `onConfirm` throwing = failure, it stays put for a retry (the error has been shown as a toast); returning `false` =
  the page blocked it itself, and it also stays put; anything else is success and the dialog closes itself. The three
  containers (`onSubmit` of `FormDialog`, and `ConfirmPopover`) share the same convention. Greying out while
  submitting and refusing to close during the request also belong to it; the page passes no busy state. While
  parameters the action collects are not filled in yet, grey out the confirm button with `confirmDisabled`; when the
  parameters need data from an endpoint (such as dropdown options), pass the query results to `queries`, and confirming
  is blocked while they are pending or failed, as with `FormDialog`.
- **Pass the success message as `success`** (same name on `FormDialog` and `ConfirmPopover`; on a `RowAction` it is
  `confirm.success`); without it, nothing is sent. Give it only to actions whose effect the screen does not show; the
  test and the counterexamples are under "Success messages" above. Do not call `toast.success` in a page.
- For an action with more than one kind of result (actually executed / only submitted for approval), pass a function
  to `success`: `success={(r) => (r.submittedForReview ? t('…') : undefined)}`. Its argument is the confirm function's
  return value, and returning `undefined` sends nothing. When the confirm function is an inline arrow, annotate its
  parameter type (`(otp: string) => …`); otherwise `success`, which comes before it, cannot infer its argument type.
  `confirm.success` on a `RowAction` takes only fixed copy; for such actions, open an `ActionDialog` from `onSelect`.
- On a table row: give the `RowAction` `confirm: { title, description, needOtp, onConfirm }`. While the button is
  exposed on the row, a popover opens next to it; once it is tucked into the "⋯" menu, a dialog is used
  automatically, and the page does not decide.
- A button in the page header or on the bulk bar that should use a popover:
  `<ConfirmPopover trigger={<Button>…</Button>} … />`.

## List page URL and pagination

- The list definition goes in the domain's API file: `export const xxxList = defineList({ queryKey, fields, fetch,
  getRowId })` (`web/src/lib/list.ts`). Each entry in `fields` picks `{ type: 'text' }`, `{ type: 'number' }`,
  `{ type: 'dateRange' }` (add `zone: 'business'` for the fixed kind) or `{ type: 'timeRange' }`; any other conversion
  is `{ type: 'custom', toParams }` (a pure function). The `queryKey` prefix matches the domain's invalidations. A list
  whose data changes slowly and whose request is heavy may add `staleTime` (milliseconds): within that time the same
  data is reused without a new request; without it, every use refetches in the background. Queries that are not lists
  set the same option in their own `queryOptions`.
- The key of a time filter is the prefix of the endpoint's field names: the key `created` sends `createdFromAt` /
  `createdToAt` (the following kind) or `createdFromDate` / `createdToDate` (the fixed kind), and the field of the
  same name in `FilterBar` uses the same `type` and `zone`. How time is passed:
  `docs/adr/admin-0003-three-meanings-of-time-and-how-to-pass-them.md`.
- The route spreads `...xxxList.route` (URL declaration plus prefetching page 1); the page does
  `const list = useList(xxxList, Route)` (`web/src/hooks/use-list.ts`), then
  `<FilterBar fields={...} {...list.filterBar} />` and `<DataTable ... {...list.table} />`. Filter field keys can only
  be keys the list definition has, so a typo fails to compile; when the field list is first stored in a variable (for
  example with `useMemo`), annotate it as `FilterFieldsOf<typeof xxxList>`, or it escapes this check.
- After adding or deleting a route file under `web/src/routes/`, run `make routes` first (done automatically while
  `pnpm dev` runs) to regenerate `routeTree.gen.ts`, then `pnpm lint`; otherwise tsc reports the new path as unknown,
  which looks like a typo in the path.
- Dropdown filters do not include an "All" option; `FilterBar` adds it. A field that must not have "All" sets
  `hideAllOption: true`.
- A filter whose options keep growing with the business uses `type: 'searchSelect'`: export a data source from the
  domain's API file (`queryKey`, batch size `pageSize`, `load`; example: `userOptionsSource` in `lib/users.ts`) and
  spread it into the field. Keyword search, loading the next batch when scrolled to the bottom, showing the selected
  item's name after a refresh, and resetting with the query are all handled by the filter bar.
- A control the built-in fields cannot express uses `type: 'custom'` and renders its own control in
  `render({ value, onChange, label })`: `value` is the value this field is editing; call `onChange` on change, and
  query, reset and refill work as usual. Follow the built-in dropdowns for the label: put `label` inside the control.
- A link to a related list goes in the `href` of a `RowAction`, generated with
  `useRouter().buildLocation({ to: '/target/path', search: { key: value } }).href`, never assembled by hand.
- Dialogs and drawers open and close with `useState`: `editing` holds an id or `'new'`, `viewing` holds an id.
