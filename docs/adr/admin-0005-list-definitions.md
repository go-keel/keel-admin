# A paged list's data wiring belongs to its list definition; the page writes only the UI

<!-- Shared file: carried verbatim; never localized outside its source repository.
     Checked by scripts/check-cross-repo-sync.sh; see docs/upgrading-protocol.md. -->

## Context

If every paged list page wires up the same data plumbing itself (which filters the URL carries, copying URL values
into a filter object, the page number, converting request parameters, the filter bar's current values and reset, the
table's pagination props), one filter is written in five or six places, and missing any of them raises no error. Three
kinds of bug come from this:

- the filter bar's draft is refilled on every re-render of the page; when the data is refetched automatically in the
  background, a filter typed but not yet submitted is wiped out;
- page number, selection and filters each live in a different place and do not talk to each other: after the filter
  changes, the previous batch's selection is still there, and a bulk action carries rows no longer visible; deleted
  rows still count as selected too;
- the same thing is written differently on each page: "All" is 0 on some and empty on others, and some pages do not
  prefetch on entry.

Changing anything common to this wiring means patching it into every list page separately.

## Decision

**Every paged list gets one list definition** (term in each repository's `GLOSSARY.md`): which filter conditions exist,
what each looks like in the URL and in the request, and which endpoint the data comes from. The URL declaration,
prefetch on entry, the request, the filter bar's current values and "Search" / "Reset", the page number and the result
set are all derived from it. The page writes only the UI: what the filter controls look like, which columns exist, row
actions, dialogs, bulk and export buttons.

Seven accompanying rules:

1. **The definition lives in the domain's endpoint wrapper**, next to the endpoints it calls; not in a separate file
   and not in the page;
2. **filter conversion has three built-in kinds (text, number, time range) plus an escape hatch**: an individual
   condition may bring its own conversion function. The kind also decides how it looks in the URL: numbers are stored
   as numbers, text as text, and time ranges are converted according to the meaning of time they represent (see
   `docs/adr/admin-0003-three-meanings-of-time-and-how-to-pass-them.md`);
3. **the router reads and writes the URL in the library's default way, unconfigured**;
4. **when the result set changes, go back to page 1; when the result set or page number changes, clear the selection;
   only rows currently visible count as selected**;
5. **"All" means no value**: it is not written to the URL nor sent to the endpoint, and the filter bar puts it first in
   the dropdown automatically;
6. **links that jump to a related list are generated by the router from the target page's definition**, not assembled
   by hand;
7. **queries follow the page's own state, and the URL is only kept in sync**: only "Search" and "Reset" change the
   effective conditions and write them to the URL (adding a history entry); with unchanged conditions they still
   refetch and stay on the current page. A URL changed by something other than a query (first open, Back/Forward, a
   sidebar link to this page, editing the address bar) is handled like a first open: restore the conditions from the
   URL, go back to page 1, fetch the data.

## Why one definition and not a few shared functions

Shared functions solve "this conversion is written a dozen times", not "this filter has to be written in six places":
the key names are still scattered across the URL declaration, the filter object, the reset list and the request
conversion, and each can still be missed. None of the three bugs above is a wrong conversion either; each is **one
piece of state managed half here and half there**: page number, selection and draft each do not know the result set
changed. Only when one thing knows both "which filters exist" and "what the result set is" can reset, back-to-page-1
and clearing the selection all derive from it.

## Why the definition does not cover controls

Filter controls differ on every page (a tree indented by hierarchy, a dropdown grouped by category), and swapping a
control is the most common change to a page. Fold the control type into the definition, and a page wanting another
control has to change the definition, while the shared part grows a string of parameters it does not understand. The
definition covers only data; the page writes the controls itself following the component library, and each side
changes on its own.

## Why the router's URL handling is not changed

By default the library quotes text that looks like a number, so ID-like filter values appear quoted in the URL; that
is the price it pays for "it reads back as text". There are two ways to remove the quotes, each bringing its own kind
of problem:

- turn off quoting with the library's one-line option: the reading side can then no longer tell whether `1.50` is
  text or a number, can only read it back as the number 1.5, and a text filter's value is silently rewritten;
- write our own "always read and write as text" rule: values are not changed, but that rewrites the library's core
  behaviour on its behalf, and we would have to maintain it.

The quotes are only unsightly and cause no errors, so they stay.

## Why the selection is cleared by result set and also intersected

"Selection does not span pages" by itself covers only page changes and page size changes. After the filter changes,
rows ticked in the previous result set are just as invisible to the user; deleted rows are no longer in the table but
are still counted and still carried by bulk actions. Clearing by result set covers the former, intersecting covers
the latter; both are invisible selections, the same reason as selection not spanning pages.

## Why queries do not follow the URL

When the URL drives queries, whether a request goes out depends on whether the URL changed: click "Search" with
unchanged conditions, the URL does not change, the cache has not expired, and nothing happens. Queries are triggered
by page state and actions; the URL is written only on query and restored on external changes, and refreshing, sharing
links and going Back to the previous query's conditions all still work.

## Why related links are not assembled by hand

A hand-assembled link has no type checking: when the target page renames a filter, that URL key is treated as unknown
and silently dropped, and the new browser tab opens the full list with no error at all. Generated by the router from
the target page's definition, a wrong key name fails to compile on the spot, and the URL is exactly what clicking
"Search" on that page would produce.

## Rejected approaches

- **Folding filter controls into the definition**: see "Why the definition does not cover controls".
- **One big component wrapping the filter bar and the table together**: the shortest pages, but the bulk bar, export,
  or any button next to the filter bar can be added only by changing the shared component.
- **Extracting shared functions**: see "Why one definition and not a few shared functions".
- **Scattered page-number and URL utilities alongside list definitions**: with two ways of writing it present at once,
  whoever copies from another page may copy the flawed one.

## Consequences

- Every paged list needs a definition first, even with a single filter.
- ID-like filter values appear quoted in the URL.
- Conversions beyond the three built-in kinds go through the escape hatch, as a function you write yourself.
